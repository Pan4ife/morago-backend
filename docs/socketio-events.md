# WebRTC & Socket.io Contract

Документация событийного контракта Socket.io-сервера Morago. Обычная OpenAPI/Swagger-документация не применима к этим событиям, поскольку они не являются HTTP-запросами.

## Подключение (handshake)

- **URL**: `ws://<host>:<port>` (порт и хост берутся из `socketio.host` / `socketio.port` в `application.properties`)
- **Аутентификация**: JWT access-токен передаётся в заголовке `Authorization: Bearer <token>` при подключении.
- Токен без валидной подписи, просроченный, `refresh`-типа, либо принадлежащий заблокированному (`BLOCKED`) пользователю — соединение отклоняется на этапе handshake.
- `userId` пользователя определяется **только** из проверенного JWT — клиент не может передать `userId` напрямую ни на одном из этапов (handshake, payload событий).

## Комнаты

| Тип комнаты | Имя | Кто состоит |
|---|---|---|
| Персональная | `<userId>` | Все активные подключения одного пользователя (браузер, вкладки, устройства) |
| Комнаты звонка | `call-<callId>` | Ровно два участника: клиент и переводчик конкретного звонка |

Персональная комната создаётся автоматически при подключении. Комната звонка создаётся по требованию — оба участника должны явно отправить `signal:join`.

## События: клиент → сервер

### `signal:join`
Вход в комнату конкретного звонка. Также рассылает остальным участникам комнаты `signal:peer-joined` с `userId` присоединившегося.

**Payload:**
```json
{ "callId": 42 }
```

**Поведение:** проверяется, что отправитель — клиент, переводчик этого звонка, либо админ (иначе `signal:error`). При успехе — `client.joinRoom("call-42")`.

**Ответ:** `signal:joined` (успех) или `signal:error` (отказ).

---

### `signal:offer`
SDP-offer — первый шаг установления WebRTC-соединения, инициируется звонящей стороной.

**Payload:**
```json
{ "callId": 42, "sdpMessage": "v=0\no=- ... " }
```
`sdpMessage` — до 15000 символов, содержимое не проверяется сервером по смыслу (непрозрачная полезная нагрузка).

**Поведение:** ownership-проверка → пересылается второму участнику комнаты `call-42` (сам отправитель исключён из рассылки).

---

### `signal:answer`
SDP-answer — ответ на offer от второй стороны. Структура идентична `signal:offer`.

**Payload:**
```json
{ "callId": 42, "sdpMessage": "v=0\no=- ... " }
```

---

### `signal:ice-candidate`
Один ICE-кандидат (сетевой маршрут для P2P-соединения). Отправляется многократно за один звонок, по одному кандидату за раз (ICE trickling).

**Payload:**
```json
{ "callId": 42, "iceCandidate": "candidate:842163049 1 udp 1677729535 192.168.1.5 54321 typ srflx ..." }
```
`iceCandidate` — до 900 символов.

**Поведение:** ownership-проверка → пересылается второму участнику комнаты.

---

### `signal:leave`
Участник покидает звонок.

**Payload:**
```json
{ "callId": 42 }
```

**Поведение:** ownership-проверка → `client.leaveRoom("call-42")` + уведомление второго участника через `signal:leave`.

## События: сервер → клиент

| Событие | Когда отправляется | Payload |
|---|---|---|
| `signal:joined` | Успешный `signal:join` | — |
| `signal:peer-joined` | Второй участник выполнил `signal:join` | `userId` (Long) |
| `signal:offer` | Второй участник прислал `signal:offer` | `sdpMessage` (String) |
| `signal:answer` | Второй участник прислал `signal:answer` | `sdpMessage` (String) |
| `signal:ice-candidate` | Второй участник прислал `signal:ice-candidate` | `iceCandidate` (String) |
| `signal:leave` | Второй участник вызвал `signal:leave` | — |
| `signal:error` | Ownership-проверка не пройдена для любого из событий выше | Строка с текстом ошибки |

## События жизненного цикла звонка (сервер → клиент)

Отправляются через персональную комнату (`room = userId`), не через комнату звонка. Публикуются после успешного коммита транзакции (`@TransactionalEventListener(AFTER_COMMIT)`) — событие никогда не приходит, если операция была отменена/откачена.

| Событие | Когда | Получатель | Payload |
|---|---|---|---|
| `call:incoming` | Клиент создал звонок (`POST /calls`) | переводчик | `callId` |
| `call:started` | Переводчик начал звонок | клиент и переводчик | `callId` |
| `call:finished` | Звонок завершён (вручную или по таймауту) | клиент и переводчик | `callId` |
| `call:cancelled` | Клиент отменил звонок | переводчик | `callId` |

## События платежей (сервер → клиент)

Та же гарантия — публикуются только после коммита транзакции.

| Событие | Когда | Получатель | Payload |
|---|---|---|---|
| `transaction:charged` | Списание с клиента за завершённый звонок | клиент | сумма |
| `transaction:earned` | Начисление переводчику за завершённый звонок | переводчик | сумма |
| `transaction:topped-up` | Пополнение баланса | сам инициатор | сумма |
| `withdrawal:created` | Переводчик создал заявку на вывод | переводчик | id, статус, сумма |
| `withdrawal:approved` | Админ одобрил заявку | переводчик | id, статус, сумма |
| `withdrawal:rejected` | Админ отклонил заявку | переводчик | id, статус, сумма |
| `withdrawal:paid` | Админ отметил заявку выплаченной | переводчик | id, статус, сумма |

## Известные ограничения

- `socketio.allowed-origins=*` — временная заглушка на время отсутствия фронтенда; `setOrigin()` у netty-socketio не поддерживает многодоменный allow-list "из коробки", нужна ручная проверка `Origin` в `AuthorizationListener`.
- Аннотации валидации (`@NotNull`, `@Size`) на DTO не запускаются автоматически в Socket.io-контексте (в отличие от REST через `@Valid`) — сервер полагается на ручные `null`-проверки внутри листенеров.
- Продление истёкшего access-токена на активном соединении не реализовано — клиент должен переподключиться с новым токеном после `POST /auth/refresh`.
